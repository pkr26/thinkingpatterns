# Fathom: independent project audit and improvement plan

Audit date: October 3, 2026. Source baseline: commit 9c1ba47508f474afc5f70588dd2771d80c2eece7. Scope: all 781 Git-tracked project files. Application source was left unchanged.

## Assessment: 61/100

Fathom has a thoughtful foundation: client-side authenticated encryption, deliberate consent, deterministic analysis, versioned database migrations, offline writing, a clinician portal, and substantial automated testing. It is not ready for a public release in its current state. Several supported workflows can lose writing or recordings, make clinical notes unreadable, fail password recovery, or prevent the native app from starting. These defects outweigh polish and test-count achievements.

The best next investment is making every existing promise dependable: a saved entry must remain recoverable, a key change must preserve all encrypted data, a revoked permission must stay revoked, and the app must work on actual supported devices.

This is a weighted reviewer assessment of the checked-out project, not a certification, clinical efficacy score, or percentage of passing tests. A score above 90 would require verified user outcomes and release evidence, not merely resolving this report's findings.

## Release blockers and verified high-priority findings

“High” below means serious data, privacy or functional impact under the stated conditions. It does not mean every item is an unauthenticated remote security exploit. P0 means fix before public release; it is a delivery priority.

### 1. Both native launchers request a JS root that is not registered — P0 / high

[mobile/index.js:23](/Users/pradeepreddy/Desktop/mental_health_application/mobile/index.js:23) registers Fathom. [Android MainActivity:16](/Users/pradeepreddy/Desktop/mental_health_application/mobile/android/app/src/main/java/com/mindpattern/MainActivity.kt:16) and [iOS AppDelegate:45](/Users/pradeepreddy/Desktop/mental_health_application/mobile/ios/MindPattern/AppDelegate.swift:45) request MindPattern. This is a conclusive component-name mismatch in the supported startup path. It was not device-tested.

Use one stable internal root identifier across JS, Android and iOS. Branding should not require changing cryptographic domains or internal component names. Add an actual signed cold-boot smoke test on both platforms; static project-file presence is insufficient.

The iOS Health bridge also declares a category on a merely forward-declared class at [bridge:48](/Users/pradeepreddy/Desktop/mental_health_application/mobile/ios/MindPattern/HealthBridge/RCTAppleHealthKit+MindPatternStateOfMind.m:48). An isolated Objective-C compiler rejects it. Import the full public class interface and build the target with the actual pod/toolchain.

### 2. Clinician key changes can make valid saved notes unreadable — P0 / high

[PatientsView:292](/Users/pradeepreddy/Desktop/mental_health_application/portal/src/views/PatientsView.tsx:292) binds legacy migration decryption to username; existing notes use the therapist UUID. Failed decryptions are skipped, credentials rotate, and the old password-derived note key is retired. A real encrypted legacy note plus the actual change-password action reproduced this loss of access.

Separately, [crypto.ts:50](/Users/pradeepreddy/Desktop/mental_health_application/portal/src/crypto.ts:50) derives v2 note keys from the sharing identity private key, while [PatientsView:489](/Users/pradeepreddy/Desktop/mental_health_application/portal/src/views/PatientsView.tsx:489) replaces that identity without migrating notes. A second real-crypto probe shows existing v2 notes no longer decrypt. The UI promises notes are unaffected.

Fix UUID binding immediately and make unreadable migration inputs explicit failures. The durable design is an independently generated notes data key, wrapped separately from the replaceable sharing identity. Include every note revision. Change notes, wraps and credentials as an atomic or resumable transaction, with a verified recovery path after full reload. The current documented multi-request failure window can strand keys even beyond these two specific bugs.

### 3. “Saved” does not consistently mean durable — P0 / high

[web/kvstore.ts:135](/Users/pradeepreddy/Desktop/mental_health_application/web/src/kvstore.ts:135) suppresses persistence exceptions. A quota-failure probe shows enqueue succeeds while queue length remains zero; Entry then clears the editor/draft and announces success. A second component probe shows new writing typed during an in-flight save is erased by completion at [Entry:471](/Users/pradeepreddy/Desktop/mental_health_application/web/src/views/Entry.tsx:471).

Propagate typed storage failures. Acknowledge a save only after durable persistence or server receipt; retain text and drafts on failure. Track editor revisions and clear only the submitted revision. Distinguish “saved on this device,” “synced,” and “not saved” with actual state behind each label.

### 4. Offline voice reconnection and replacement can discard recordings — P0 / high

[mobile/store.tsx:213](/Users/pradeepreddy/Desktop/mental_health_application/mobile/src/store.tsx:213) flushes text and audio concurrently. [audioQueue:182](/Users/pradeepreddy/Desktop/mental_health_application/mobile/src/audioQueue.ts:182) deletes an attachment after a 404, even when its parent entry is still pending upload. A normal fast-audio/slow-parent sequence can therefore delete the only retained take.

The audio flusher also removes a storage key after awaiting an older upload without checking the current row identity. A replacement take can be deleted by late completion. After clear/sign-out, a late 401 can write an erased row back. Independent tests reproduced these paths.

Use a dependency-aware outbox: parent acknowledgment precedes attachment upload. Serialize flushes per account/origin; attach a generation and row revision to every mutation; compare identity after every await. Retain ambiguous failures, report per-item status, and let users choose destructive eviction. Accepted large audio rows can exceed Android storage read limits; use encrypted file blobs with a small transactional index rather than multi-megabyte AsyncStorage records.

### 5. Password recovery has both protocol and revocation failures — P0 / high

[mobile/recoveryFlow.ts:83](/Users/pradeepreddy/Desktop/mental_health_application/mobile/src/recoveryFlow.ts:83) passes the complete processing-session JSON object as a token. The real header becomes an object string rather than session_token; the reset fails. The test mock returns a bare string and hides the mismatch. Validate and type the response at the API boundary.

The same flow automatically retries v1 with the raw recovery key after a server-supplied scheme-mismatch error. Under the stated hostile-server threat model, this lets a compromised server solicit the secret that v2 was designed to withhold. Encode the scheme in the locally held kit and never downgrade a v2 kit based solely on a remote error. This is not a claim about a passive TLS interceptor.

On the backend, [auth.py:430](/Users/pradeepreddy/Desktop/mental_health_application/backend/app/api/auth.py:430) retains recovery material across expensive asynchronous verification without a fresh lifecycle check before issuing a token. A controlled race reproduced recovery removal returning 204, followed by the in-flight recovery returning a live token despite recovery being disabled. Recheck enrollment, activity and epoch under the lifecycle fence after hashing; serialize revocation and issuance or use a conditional database update.

[account.py:1236](/Users/pradeepreddy/Desktop/mental_health_application/backend/app/api/account.py:1236) pops a processing key for recovery reset without a finally block to zeroize it. The successful synthetic reset left the popped bytearray nonzero. Match normal password-change cleanup, including failure paths. Python zeroization remains best effort; this finding concerns a missing explicit cleanup, not a guarantee that all runtime copies can be erased.

### 6. Legacy data-key rotation omits encrypted stores — P0 / high

[mobile/rotation.ts:645](/Users/pradeepreddy/Desktop/mental_health_application/mobile/src/rotation.ts:645) migrates selected stores while omitting the safety plan, pending questionnaire and retained audio queue. These remain under a retired key after v1 rotation. Backend rekey paths at [insights.py:617](/Users/pradeepreddy/Desktop/mental_health_application/backend/app/api/insights.py:617) handle entries, insights and measures but omit stored audio attachments. This is a source-confirmed incomplete migration; a full retained-audio migration journey was not device-tested.

Maintain one registry of every data-key-bound store, version, migration and erasure handler. Do not retire a key until every durable object has migrated and its readability has been verified. Test pending and uploaded audio, plans, questionnaires, drafts, notes/revisions and restart checkpoints. V2 password changes retaining the same random data key do not have this particular v1 failure.

### 7. Microphone acquisition can outlive the screen — P0 / high

[web/audio/recorder.ts:193](/Users/pradeepreddy/Desktop/mental_health_application/web/src/audio/recorder.ts:193) awaits permission and starts recording without checking whether the operation still owns the screen/session. A deferred-permission test grants the stream after unmount; recording starts and the track is not stopped. Two pending starts can orphan the first stream.

Reserve acquisition synchronously, invalidate its generation on reset/unmount/lock, and stop every late stream immediately. Use one recording owner and test every permission and teardown boundary. Add equivalent ownership handling to native and portal playback preparation; their late plaintext-file/Blob-URL cleanup gaps are currently source-supported risks rather than device-reproduced leaks.

### 8. The pattern screen renders a different response from the one it validates — P0 / high

[web/Patterns.tsx:159](/Users/pradeepreddy/Desktop/mental_health_application/web/src/views/Patterns.tsx:159) validates one insights response, then fetches another at :186 and renders it without checking the new state_seq. A component probe returned valid seq20 first and validly encrypted seq1 second; the old observation appeared without a freshness error.

Have reconciliation return the exact validated payload and render it. Require account/session ownership and generation validation after all delayed reads. A check on an earlier response does not protect a later response.

### 9. A real questionnaire tap cannot record the result — P0 / high

[MeasuresScreen:191](/Users/pradeepreddy/Desktop/mental_health_application/mobile/src/screens/MeasuresScreen.tsx:191) defines submit(retryRecord?) and passes it directly to native onPress. React Native supplies an event, which the handler treats as the retry record. A real-component test with a native-shaped event reproduced “Not recorded” and no create call.

Wrap the callback to call submit with no argument; use a separate retry action and event-correct test helpers. Test the complete questionnaire journey with the actual native callback contract.

HealthKit integration also uses an incomplete factory selector and sends valence values −2 to +2. Apple's factory includes metadata and its valence scale is −1 to +1. Correct both and test real supported-device writes, including intermediate moods. [Apple factory documentation](https://developer.apple.com/documentation/healthkit/hkstateofmind/stateofmindwithdate%3Akind%3Avalence%3Alabels%3Aassociations%3Ametadata%3A?language=objc), [Apple State of Mind session](https://developer.apple.com/videos/play/wwdc2024/10109/).

### 10. Valid brief journals can crash pattern recomputation — P0 / high

[brain.py:3101](/Users/pradeepreddy/Desktop/mental_health_application/backend/app/services/brain.py:3101) checks the without-theme mood group but divides by the length of the with-theme group without ensuring it is nonempty. Removing theme words from entries consisting solely of “work” leaves no independent mood evidence. Eight such days plus 32 ordinary text days cause ZeroDivisionError in the pure brain update.

Require sufficient independent observations on both sides after filtering. Skip an unsupported association while retaining all other analysis. Add varied short/empty/tag-only/text-only corpora and whole-recompute fault isolation, not merely a guard tailored to this exact sentence.

### 11. Audit MAC verification can be downgraded to legacy acceptance — P1 / high

[api/_audit.py:495](/Users/pradeepreddy/Desktop/mental_health_application/backend/app/api/_audit.py:495) treats a missing MAC as an accepted legacy row. A controlled database-only modification of a newly sealed row, with an unkeyed hash recomputed and MAC removed, passed verification even with the external journal enabled. The journal's sequence comparison does not pin the row's seal in this case.

This weakens the promised resistance to database-writer tampering; it is not an anonymous HTTP attack. Define an authenticated MAC-required cutover/version and reject missing MACs after it. Anchor trusted heads with authenticated seals outside the database. Test edits, removed seals, tail replacement, truncation and retention separately.

### 12. The documented offline export tool cannot open current v2 exports — P0 / high

[decrypt_export.mjs:142](/Users/pradeepreddy/Desktop/mental_health_application/mobile/tools/decrypt_export.mjs:142) derives the legacy password-based data key for every bundle. It never unwraps the random v2 data-key envelope. A valid synthetic v2 envelope and entry decrypted independently, but the actual CLI, run from mobile with the correct password, reported 0/1 entries and exited 1. This breaks the documented export-then-delete recovery path for current v2 accounts.

Support the explicit key scheme and validated envelope parameters; obtain the account username locally for the existing envelope AAD because the server export omits it. Preserve privacy through a prompt or a compatible export/recovery format. Also restore kept audio rather than ignoring the export's audio array. Test v1/v2, empty and populated accounts, entries/insights/measures/audio, password change and restoration after account deletion. Offer a straightforward readable export inside the unlocked client, with deliberate destination/privacy controls.

## UI/UX: how to make this feel exceptional

The visual direction is coherent and calm in code: themed patient screens, restrained clinical UI, deliberate error copy, reduced-motion support and accessible control intent. Preserve those strengths. Beauty should support the main task: helping someone record their experience and understand it without friction or pressure.

### The patient's first minute

Offer a minimal optional mood/check-in and a short journal entry. Explain the privacy model at the point it matters, in one or two plain sentences with details available. Show exactly what was saved and where. Allow recovery setup with a clear save/verify ceremony. The first session should give immediate value even though deeper statistical patterns require enough observations.

The 30-active-day threshold can protect against premature inference, but it must not create a month of apparently empty value. Before inference, offer private readback, simple user-entered summaries and optional reflections with no unsupported personalized claims. Never invent a pattern just to populate a screen. Let users pause reminders and resume without guilt.

### Everyday journaling and recovery

Use one clear daily entry path, durable drafts, readable history detail and simple edit/delete controls. Keep newer writing intact during save. Make offline limitations understandable: current web offline writing requires an already-loaded authenticated shell; it is not a tested installed, cold-start offline vault. Native history also does not provide a complete offline local history cache.

A person should be able to tell whether their latest entry is durable locally, acknowledged remotely, waiting, or failed. Offer explicit retry and export for pending recordings. Avoid silent capacity eviction. Navigation back, backgrounding, screen lock, process death and network loss must be ordinary, recoverable states.

### Patterns that people can understand and challenge

Each card should say what was observed, over which distinct days, how recent it is, what evidence supports it, and how uncertain it is. Keep association separate from causation and textual sentiment separate from self-reported mood. Let users mark an observation useful, inaccurate or irrelevant and see how that affects future presentation. Evidence should be readable without forcing edit mode.

Fix unit errors and avoid displaying a confidence number that users could mistake for diagnostic probability. Explain why a card is absent or tentative. Present a calm optional weekly review; measure whether it improves understanding, rather than optimizing streaks or notification opens.

### Clinician workflows

Prioritize patient search, longitudinal review, trustworthy sharing status and note preservation. Preserve drafts on chart changes, conflict, idle lock and reload using encrypted patient/note/pattern-scoped storage. Offer a clear comparison when an edit conflicts rather than erasing the user's work. Support deliberate sharing expiry and access review once the core reliability is established.

Use URL-based chart/history navigation with browser back/forward and appropriate deep links. Add convenient TOTP QR enrollment alongside manual setup. Printed/exported summaries need separate privacy and layout verification. Clinical instrument scores and crisis phrases should remain prompts for appropriate human review; the product must accurately describe whether anyone is monitoring them.

### Accessibility and language

Aim for WCAG 2.2 AA on the web, with complete keyboard tasks, visible/unobscured focus, reflow, programmatic group names, accessible authentication and chart text/table equivalents. Automated axe/contrast tests are useful but do not cover real assistive technology, zoom, touch layout or native platform behavior. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/).

Test VoiceOver, TalkBack and a desktop screen reader on actual devices; cover maximum text size, 320px layouts, zoom, keyboard-open forms, portrait/landscape, dark mode and reduced motion. Replace cramped horizontal questionnaire choices with adaptable layouts. Consume real safe-area insets and reduce six-item navigation density if usability sessions justify it.

English/Spanish catalog key and placeholder parity is strong. Review actual clinical phrasing, cultural assumptions, expansion and on-screen language switching with native speakers. Structural translation parity is not linguistic or clinical validation.

## Frontend, state and performance architecture

Create a small set of explicit domain workflows: authentication/vault, durable writing, synchronization, recording/playback, sharing, credential rotation and clinical notes. Model states and transitions; use one ownership token containing account, session, origin, resource and revision where relevant. Every delayed completion must prove it still owns the operation before mutating storage or UI.

Make a persistence result a domain contract, not a platform fallback. A storage method returning successfully must mean the write committed. Use a transactional outbox with stable operation IDs, dependency ordering, revision-aware acknowledgments and unambiguous retry semantics. Separate pending user data from disposable caches. Include sync repair and user-visible recovery of partially completed operations.

Generate or share typed API contracts and validate JSON at runtime. Remove any from auth/session/recovery/key-change results. Validate decrypted payload versions, finite numbers, dates, enums and length limits; preserve unknown metadata during edits. Keep malformed-record errors distinct from empty data so a failed decrypt does not silently become “no safety plan.”

Refactor large modules by workflow responsibility, not arbitrary file-size limits. backend account has 2,456 lines, insights 2,127, therapist 2,376 and brain 5,378; some functions exceed 500 lines. Large client screens and API modules similarly combine transport, cryptography, persistence and UI. Extract coherent transaction services and pure domain logic while preserving existing behavior with integration tests. Consolidate duplicated client crypto/protocol code where platform constraints permit; keep native adapters explicit.

The patient web build bundles 851.40 kB of initial JavaScript (254.96 kB gzip); portal is 277.83 kB (86.22 kB gzip). Lazy-load heavy settings/history/clinical views, locale catalogs and lexicons. Debounce or move expensive sentiment analysis off the main thread. Page and cancel decryption work; do not decrypt an entire lifetime of history to show 30 rows. Batch encrypted map reads/writes to avoid repeated whole-map rewrites.

Measure cold start, typing delay, warm local save, sync time and memory on inexpensive devices and a slow network. Proposed initial targets, to refine after a measured baseline: first useful check-in within one minute, warm local save acknowledgment within one second at p95, no long input stalls, and loading progress for genuinely long work. These are proposed product goals, not measured achievements. Gather only consented aggregate timing/status information; never journal text or identifiable clinical payloads.

## Backend, database and operations

Retain authenticated encryption/AAD separation, bounded pagination, collection revisions, strict error envelopes, off-loop expensive work, quotas and database timeout configuration. The schema has deliberate uniqueness constraints and indexes for the main access paths. SQLite foreign-key/WAL behavior and PostgreSQL coverage are useful investments. Twenty-eight migrations form one complete graph with head a3f7c1d9b5e2.

Move irreversible multi-call changes into atomic or recoverable server transactions: note migration, credential/wrap changes, sharing-key changes and rekey acknowledgments. Use conditional updates on versions/epochs and fresh reads at transaction boundaries. Consider database CHECK constraints for positive versions/nonnegative counters and explicit status domains after validating existing data. Keep metadata revision and content mutation in the same transaction.

Database commits cannot atomically delete object-store bytes. Use a durable object-deletion outbox/tombstone and retry until confirmed, with inventory reconciliation. Current best-effort account cleanup can orphan local-store ciphertext once its DB row is gone; S3 lifecycle is only a secondary backstop. Verify audio retention, deletion, export and backup coverage explicitly.

Current correctness depends on a single API process/host with in-memory locks, rate counters and processing keys. That is a legitimate bounded deployment model, but it needs tested fault behavior and measured capacity. Monitor guard ownership continuously and fail readiness when it is lost. Do not scale replicas until shared admission/rate/revocation/locking semantics and secure ephemeral processing-key ownership are designed. Redis alone is not a complete answer to key custody or transaction fencing.

Fix the configured body concurrency mismatch and test allowed configurations at memory limits. Add realistic workload profiles: simultaneous saves, recomputes, large histories, audio uploads, export, key changes and slow clients. Measure query plans and p95/p99 latency before changing architecture. Do not introduce microservices or infrastructure layers just to appear scalable.

The deployment includes digest pins, file-mounted secrets, resource limits, no-new-privileges, restrained access logs, readiness checks, encrypted/MAC-authenticated backups and provisioned monitoring. Make the production checklist executable and demonstrated: notification delivery, disk capacity, public TLS, object deletion, off-site backup freshness, restore, schema upgrade and rollback. Default readiness/API monitoring alone does not establish all these properties.

Correct and rehearse the exact backup recovery instructions on a separate database. Explicitly choose RPO/RTO, retention and key custody; proposed beta goals can begin at 24-hour recovery-point and four-hour recovery-time targets if that matches the intended service, then improve them from measured drills. These targets are planning proposals. Monitor the remote backup destination, not only a local heartbeat. Inventory accepted dependency risk and fix current mobile advisories through reviewed compatible updates; do not blindly run a force-upgrade command.

Use an evidence-backed security baseline based on [OWASP ASVS](https://owasp.org/projects/asvs) and [OWASP MASVS](https://mas.owasp.org/MASVS/), then an independent review of the actual release. Standards provide verification structure; adopting them does not itself certify this app.

## Scientific validity, safety and privacy promises

The deterministic brain uses thoughtful controls: day-level grouping, effect thresholds, autocorrelation adjustment, multiple-testing correction and repeated qualification. These support cautious observation. They do not establish that an observed pattern is clinically meaningful or that the product improves health.

A fresh 2,000-run-per-setting Monte Carlo diagnostic produced raw detector p≤.05 frequencies from approximately 0.5% to 5.9%, with different behavior by series length and autocorrelation. That is a limited marginal diagnostic, not a validated end-to-end false-discovery rate or a guarantee of 5% user-level risk. Repeated sliding windows and qualification on overlapping evidence need their own evaluation; recomputation on a new day is not independent replication.

The year simulation's CSV/JSON data are internally consistent: 13 personas, 8,629 entries and 366 recorded checks. Synthetic personas, planted signals, fake transcription/LLM responses and comparison against the same engine do not replace an independent oracle or prospective human evaluation. Current claims that it covers every endpoint/every blob are inaccurate; some newer routes are absent and encrypted blob checks are sampled.

Define the intended population, supported languages, safe claims and primary user outcome before optimizing heuristics. Use independent held-out longitudinal corpora, missingness and multiple-entries/day cases, negation/quotation/third-person/idiom cases, multilingual/dialect review, annotator agreement and user-understood uncertainty. Evaluate sensitivity, specificity, calibration, per-user false observations and failure modes separately. Include clinicians and people with lived experience in usability and safety review.

Then conduct an appropriately reviewed prospective feasibility study, followed by a study suited to any health-benefit claim. The repository contains a draft protocol/self-assessment, not evidence of completed independent validation or approval. NIMH identifies effectiveness, privacy, audience fit and overselling as central concerns for mental-health apps, and describes the value of collaboration between researchers, clinicians and engineers. [NIMH mental-health technology overview](https://www.nimh.nih.gov/health/topics/technology-and-the-future-of-mental-health-treatment).

Preserve offline help and user control. Avoid equating textual sentiment, self-report or questionnaire scores with diagnosis, predicting crisis from unvalidated heuristics, or implying real-time clinical monitoring where none exists. A filter is not enough to make arbitrary generated advice safe. Before displaying LLM narratives, address the demonstrated unsafe-language bypass and use a bounded, clinically reviewed output design. Current web/portal do not display those narratives, so consented plaintext egress can incur risk/cost without a visible narrative benefit.

Privacy messaging should consistently say what is true: client-encrypted storage; metadata visible to the service; temporary server plaintext during requested processing; separate third-party consent; therapist access until revoke with already-downloaded data unretractable; disclosed backup/audit retention. The backend's “zero-knowledge” description is stronger than this architecture. Complete operator templates, disclosure contacts and deployment-specific legal review before publication; technical controls alone do not establish legal compliance or medical-device classification.

## Prioritized program toward an outstanding app

These are effort bands and acceptance gates, not guaranteed calendar estimates. Team size, migration compatibility and supported devices determine timing.

| Phase | Work | Exit evidence |
|---|---|---|
| **0: release stabilization — first 1–2 engineering cycles** | Native root/build/API fixes; questionnaire/recovery/export repair; note custody; durability and queue ordering; microphone ownership; freshness; brain empty-group guard; complete legacy-store migration | Both signed native installs cold-boot; real API/crypto journeys pass; every seeded saved/pending object remains readable after rotation/recovery/reload; no false save acknowledgment |
| **1: dependable domain core — next 2–4 cycles** | Typed/runtime API schemas; shared ownership/generation; transactional outbox; atomic/resumable credentials; encrypted drafts/conflicts; deletion retry; audit/version fences; trustworthy CI gates | Fault injection at every network/storage boundary; kill/restart during changes; two clients/tabs; revoke/clear wins late work; backup restore succeeds |
| **2: product and accessibility — run alongside phase 1 after reliability fixes** | Fast check-in, useful pre-threshold value, clear sync/retention, readable evidence, navigation, clinician workflow and language/accessibility work | Observed task success and comprehension across representative users, including assistive technology; critical journeys work at large text/zoom and slow networks |
| **3: evidence and operations — before broader launch** | Independent release review; measured device/load budgets; incident/restore drills; provider/deletion verification; prospective validity/feasibility work | Published limitations, actual operational SLO baselines, signed review artifacts and appropriately supported product claims |
| **4: differentiation — earned by evidence** | Better personalized reflection, optional clinician collaboration and integrations selected from user research | Demonstrated benefit, comprehension and privacy-preserving reliability improve; additional features meet the same acceptance gates |

Start with a compact set of full journeys using real cryptography and the actual API/persistence layer:

1. Register → write → durable local acknowledgment → offline → app/process restart → reconnect → verify text and retained audio.
2. Old and v2 account → create every supported encrypted object → rotate/recover → full reload → verify every object and revision.
3. Patient shares → clinician reads/writes note → identity/password change → reload → note still readable → revoke → later requests blocked.
4. Save while editing → late responses → account switch/lock/unmount → newer writing preserved, tracks stopped and stale state rejected.
5. Storage quota/read failure → interrupted export/delete/migration → honest status and resumable recovery.
6. Actual device cold boot → Face ID/cancel → questionnaire → recording/HealthKit where enabled → offline help → accessible navigation.

Require these as release gates. Keep fast unit tests, but reduce reliance on source-string pins and mocks that reproduce implementation assumptions. Repair the mutation-score shell gates and require complete results; actual low mutation scores should fail, healthy scores should pass. Maintain a current route inventory and label historical simulation results with exact scope.

Suggested beta scorecard:

| Outcome | Acceptance intent |
|---|---|
| Saved data | Zero acknowledged-save losses in the supported fault/restart matrix; all compatibility fixtures remain recoverable |
| Key custody | Complete readable-object checks after every supported rotation/recovery and failure checkpoint |
| Permissions | Revocation, lock, account switch and erasure defeat late work under concurrent tests |
| Usability | Users complete key tasks and correctly explain save/sharing/processing status in observed sessions |
| Accessibility | All critical tasks completed with supported screen readers and maximum text/zoom settings |
| Performance | Measured low-end device/network budgets; stable input responsiveness and bounded memory |
| Safety/evidence | Reviewed claims and wording; published uncertainty/failure boundaries; benefit evaluated with appropriate study design |
| Operations | Demonstrated restore/deletion/alert delivery; measured incident readiness and release rollback |

No audit can prove “the best application ever.” The practical ambition is stronger: become exceptionally dependable at a clear, valuable purpose, demonstrate that value with users, and protect their trust at every boundary. Fathom's existing investment makes that a credible direction. The current priority is completing and verifying those promises.
