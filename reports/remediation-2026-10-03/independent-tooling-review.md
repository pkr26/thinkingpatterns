## Verified findings

1. **Moderate: mutation comparison can pass after runtime breakage.** `redteam/mutation_campaign_2026-09-22_frontend/verify_kills.js:56–78` only marks erroneous/ignored next statuses unresolved when the prior mutant was a survivor. A `Killed` → `RuntimeError` transition prints `errors 1` but exits 0. Reproduced with identical source/scope/mutant identity. Reject every after-report RuntimeError and treat formerly scoreable → CompileError/Ignored transitions as unresolved instead of successful comparisons. Current standalone score-floor tool already rejects any RuntimeError.
2. **Moderate: campaign inventory is not execution completeness.** `redteam/validate_results.py:27–41` accepts one NOT-RUN row in each named campaign. Synthetic eleven-file all-NOT-RUN campaign validates eleven rows; the workflow's FINDING policy would then report residuals no longer reproduce and pass. Require an explicit permitted NOT-RUN-ID set and campaign-specific expected verdict IDs (or an equivalently verified case inventory). This is a proof/false-assurance problem, not an application-auth bypass. Existing runner properly clears old results and fails nonzero subprocess exits; that prevents stale/crashed campaigns but does not fix skipped/partial case inventories.
3. **Low/operational: oversized backup passphrases are silently truncated.** `backup/backup_mac.py:55–60` permits 4096 UTF-8 bytes and states truncated secrets are rejected. Installed OpenSSL actually encrypted under synthetic `('x' * 3000) + 'A'` and decrypted successfully under `('x' * 3000) + 'B'`. Both returned 0 and exact original plaintext, showing fd passphrase truncation. Normal generated 44-character keys are unaffected. A conservative accepted-length cap (e.g. 256 bytes) plus a common-prefix long-secret rejection test avoids silently changing existing backup derivation. Snapshot-HMAC still uses the full key, so this finding does not itself let an unauthenticated party alter a dump.

## Noncritical evidence/operational limits

- `tools/verify-postgres-upgrade.py:66–76` uses Python assertions for every post-upgrade invariant. Optimized Python removes these checks. Replace with explicit errors or fail if `__debug__` is false; ordinary new CI does not set optimization.
- Its success line claims preservation of audio metadata, but the only audio assertion checks new storage_locator NULL; it does not compare the old audio ID/owner/entry/backend/storage_key/size/MIME/duration/timestamps. Compare the seeded legacy row to support that claim.
- Encrypt and tag are separate helper invocations in the worker and resolve mounted/environment secrets separately. A deliberate key-file change between those invocations can make an unrecoverable mixed-key backup. Coordinate rotation while the worker is stopped or have encryption and tagging share one resolved secret/publication operation. This was not reproduced against a real operator key and no such key was read.
- The score-floor tool checks terminal statuses/empty report/runtime errors and inclusive floor correctly. It cannot independently establish that the report covers the intended current source set without an external expected scope. No separate false-floor arithmetic bug found.
- The backup decrypt path authenticates the private disk-backed snapshot that is actually passed to OpenSSL. In-place/path replacement after authentication cannot change decrypted bytes. On missing/bad HMAC it emits no plaintext. Ordinary secret resolution is consistent; raw BACKUP_KEY is removed from the child environment and passed via inherited fd rather than argv.
- Disposable `_test` URL/prior-head/empty-user-table guards, BEGIN/commit/connection close, checked Alembic subprocess and separate CI upgrade database are appropriate. No database wipe or secret-log issue found. Hosted GitHub Android/Compose/Postgres jobs were reviewed, not executed here.

## Local migration conflict assessment

Current `web/src/localRotation.ts:110` safely refuses a current value different from its recorded before/after snapshots and retains encrypted originals/checkpoint. It must not replace current writing with the staged after value automatically.

A safe automatic path for a readable current value would confirm remote finalization, authenticate that current value under the new key or retained old key using the original domain/AAD, reseal the **exact current plaintext**, and commit only through a single IndexedDB read/write compare-and-set. If current changes during crypto work, retry against the new current value. Queue processing should transform every current owned ciphertext while preserving newly added and other-owner items. Retain the staged branch as an encrypted recovery record until explicit reconciliation instead of silently discarding it.

The current `withLock('local-rotation')` is not the same lock used by every individual store writer; it therefore cannot by itself protect a future read→crypto→write conflict resolver. All writers need compatible fencing or the transactional CAS, including late unmount/autosave work. Missing/deleted, malformed/unreadable and genuinely competing plaintext branches cannot be safely guessed. Retain them and offer explicit restore/keep-both choices. After this read-only assessment, root explicitly authorized a narrow client fix. `kv.compareAndSetForMigration` now commits record comparison/replacement in one IndexedDB readwrite transaction. A real IndexedDB regression injects an independent raw writer between the preliminary read and CAS; its newer ciphertext is retained and the journal remains. Normal registered owner-scoped writes/deletes are fenced in the durable transaction while its checkpoint exists; confirmed account-erasure cleanup is allowed. Unsupported CAS adapters fail closed. The initial fix was a pending-checkpoint fence. A subsequent real-crypto IndexedDB regression proved that a suspended pre-rotation callback could overwrite a migrated safety plan after cleanup. The final correction adds captured key-bound generation permits and durable transactional checks across all registered scalar and queue boundaries, retaining the marker after cleanup. The unchanged red assertion now passes. Older direct-IDB writers remain outside this seam. Verified current-key adoption preserves ciphertext, without claiming automatic multi-device recovery. Automatic branch reconciliation remains unimplemented. See [the client evidence](web-portal.md#post-cleanup-stale-writer-correction).
