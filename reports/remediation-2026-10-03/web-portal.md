## Additional issues found while implementing and actually exercised

- **Atomic patient remote/local migration:** `web/src/localRotation.ts:57` stages all registered encrypted stores and all owned queue/reject blobs before remote mutation. It preserves each original ciphertext/AAD, stores an encrypted candidate journal under the new data key, persists the exact credential/envelope/grant payload and random key seed, and never removes original records before confirmation. Resume (`:110`) requires the authoritative remote salt to match, applies before/after comparisons and commits each replacement using a single IndexedDB readwrite compare-and-set transaction, checkpoints completed writes, and removes the journal last. A failed write or conflicting local record preserves recoverable ciphertext and the checkpoint. Old-credential login can reach Settings and repeat the intended new password to retry the saved operation; knowing a candidate key alone does not authorize pre-commit local adoption.
- **Transactional migration conflict protection:** `web/src/kvstore.ts` reads, compares and replaces a record inside one IndexedDB readwrite transaction. It never emulates CAS with separate asynchronous get/set calls. A competing raw legacy IDB write injected between the preliminary read and commit is preserved; migration rejects and retains the journal. Registered owner-scoped draft/plan/mood/feedback/measure/mute/version/queue stores also reject normal writes/deletes while that owner’s checkpoint exists, except explicit confirmed account-erasure deletions. Other owners remain writable. Unsupported injected CAS backends fail closed. The generation fence now survives successful checkpoint cleanup; see the post-cleanup stale-writer correction below.
- **Local account erasure:** `web/src/localErasure.ts` records an owner-scoped tombstone before DELETE, confirms acknowledged remote deletion, checks every registered local deletion and removes its resumable cleanup marker last. A minimal account-generation fence remains (`v`, random `nonce`, `deleted: true`), with no key tag or ciphertext, so late callbacks cannot recreate erased data. Failures lock the account and show resumable cleanup on restart. Other account scopes remain. An ambiguous, unconfirmed deletion retains data and requires an explicit user assertion before local-only erasure; it does not infer success from elapsed time or an unreadable marker.
- **Same-page BroadcastChannel self-lock:** browsers exclude only the sending channel object, not every channel on the same page. `web/src/tabLockdown.ts:22` tags each page with a random source ID and ignores its own notification. `web/tests/tabLockdown.test.ts` models multiple real channel objects and independent page module instances. Root reproduced the original bug on HTTPS and confirmed patient atomic rotation after the fix.
- **Acknowledged 204 falsely rejected:** HTTPS browser fetch exposed an empty but non-null 204 stream; constructing `new Response(stream,{status:204})` throws. Both API clients now complete/cancel any unexpected body before reconstructing/wrapping a 204 (`web/src/api/client.ts:343`, `portal/src/api.ts:213`). Regressions deliberately expose this shape. Root confirmed the clinician sends one PUT 204 and signs out, replacing four erroneous retries/server-unreachable copy.
- **Legacy clinician repair remained incompatible with custody fencing:** `portal/src/views/PatientsView.tsx:349` now verifies current/historical notes under both password generations and identity key, installs/reseals custody under the current password, confirms exact version/blob, and repairs the unchanged public/private sharing identity with CAS. A new real-crypto regression proves both password-generation notes and old revisions remain readable. New atomic flows do not create this historical intermediate state.
- **Authoritative note edit indicators:** a newly created note can have slightly different `created_at`/`updated_at` defaults without having an edit. Both interactive View history and the printed edited marker now use a provided valid integer `version > 1`. Timestamp comparison is restricted to legacy rows without a version. Five UI regressions cover version 1 microsecond drift, version 2 equal timestamps with genuinely readable revisions, edited/unedited legacy rows and an invalid provided version; version 2/history remains accessible on screen and in print.
- **Exact accessible password name:** `portal/src/ui.tsx:105` assigns input ID and explicit label/htmlFor; Show password is a sibling control. DOM/axe regression requires the input name to be exactly `Password`.
- **Evidence units/copy:** sample_entries and distinct sample_days render separately; old payloads without sample_entries show legacy/unverified units. Density/confidence are described as evidence heuristics, not diagnostic probability. Trend charts include textual/table equivalents; History supports full readback. Patient EN/ES copy acknowledges password/recovery-kit access accurately; web recovery-kit creation/use is not implemented.
- **Runtime lifetime:** patient session/catalog/migration adoption is generation-fenced against logout/expiry/unmount; stale callbacks cannot resurrect a session. Views support browser hash back/forward routes without authenticated data in URLs.
- **Performance:** eight authenticated patient views and full EN/ES catalogs load after authentication. The generated pre-auth subset preserves synchronous login/crisis copy. Clinician TOTP QR generation stays local and loads only when its secret is revealed. No external QR service receives the secret.
- **Additive encrypted-entry compatibility:** web History now passes its original authenticated payload into encryption. Only unknown additive fields are retained; every known field is rebuilt from the edited payload so omitted channels cannot leak back. Nested additive metadata, original creation time, time bucket and valid historical energy survive a real encrypted History-edit round trip. The mobile owner implements the same filter/precedence contract. Unknown payload versions and malformed known optional fields remain rejected.

## Post-cleanup stale-writer correction

A meaningful pre-fix regression suspended `saveSafetyPlan(oldKey, ...)` after real encryption, completed local rotation and checkpoint removal, then released the original callback. The callback resolved successfully and replaced the migrated record with old-key ciphertext. The unchanged rejection assertion failed in [the retained red reproduction](validation-logs/mindpattern-web-post-cleanup-race-repro.log); it passes after the correction.

The key-value seam now checks an account-scoped durable generation inside the same IndexedDB readwrite transaction as each registered mutation. Key-bound producers capture a permit before encryption/network work; newly queued entries must carry that producer permit. Existing queue metadata movers retain their captured generation through insertion, rejection, retry/requeue, quarantine and flush commit. The journal seals its before/after generations, advances generation with CAS before destination rewrites, and leaves the marker after journal cleanup. Older journals durably add these fields before advancing. An erased account keeps a minimal deleted fence without content/key-tag material. This closes the demonstrated current-client post-cleanup overwrite and resurrection races; it does not authorize raw legacy direct-IDB writes or silently merge branches.

A fresh authenticated login may adopt its verified current key's generation with a session-current guard checked at the durable CAS. Adoption changes no encrypted record. The test intentionally retains an old ciphertext that fails under the new key and succeeds under the retained original key; retention is recovery evidence, not proof of automatic multi-device recovery. Missing old-key/KDF bindings, interrupted rotations on separate devices, and independent newer writing still require the complete acceptance matrix and explicit reconciliation.

## Export privacy audit correction

The narrowly authorized `redteam/h_privacy.py` update distinguishes intentional public recovery metadata from plaintext content. It creates real v1/v2 accounts, requests fresh exports, checks exact immutable canonical username/UUID, version and self-contained salt/KDF/envelope metadata, recovers the data key from the export plus password alone and authenticates a unique encrypted journal sentinel. A pure inspection helper additionally detects nested plaintext journal/password sentinels or raw data/authentication keys in base64, hex or byte-array form; malicious synthetic responses prove those checks reject leaks. Required identity is retained for AAD interoperability; H1 metadata inference remains a FINDING. H2 content leakage, unauthenticated export and live erasure report BLOCKED.

## Release limits and evidence needed for a credible 90+ score

Code and green tests do not establish a 90+ score by themselves. These client fixes close the mapped source findings, but the following gates must remain visible:

1. Real deployment owner/contact/canonical URL must replace security.txt examples before the patient release gate passes. No invented owner values or bypass was added.
2. Real devices must exercise microphone allow/deny/revoke, recording interruptions, audio codecs/playback, QR scanner readability and current Safari/Firefox/Chrome compatibility. Web Locks and durable IndexedDB are required for acknowledged patient shared mutations; unsupported/private/restricted hosts fail explicitly.
3. Human keyboard/screen-reader audits must cover complete patient/clinician security and note-edit journeys, focus after errors, 200–400% zoom, reduced motion and high contrast. Automated axe checks and 390px browser checks cover only part of accessibility.
4. Representative devices/network traces and long histories must establish LCP/INP/CLS, authenticated-route latency, memory/voice throughput and multi-patient scalability. The initial JS gzip budgets now pass; no percentile performance claim is made.
5. Clinical/domain experts and users must validate evidence wording, early-month usefulness, safety-plan comprehension and clinician workload. Heuristic confidence is not validated clinical probability; no “best application ever” or diagnostic efficacy claim follows from these tests.
6. A contended local migration record is retained and blocked by transactional CAS; there is no automatic merge or end-user multi-version conflict chooser for that rare state. [Operational recovery guidance](local-migration-recovery.md) requires retaining both encrypted branches/checkpoint and authenticating the current branch before any restoration. Current registered-store mutations require their captured durable generation after rotation and remain fenced after checkpoint deletion. Older clients that write IndexedDB directly can bypass this client seam; they require coordinated version retirement. Verified fresh-login key adoption preserves existing ciphertext but does not establish competing-device recovery: without its retained old-key/KDF binding and authenticated current plaintext, local re-encryption cannot be inferred. The complete competing-device/recovery matrix and separate-tab draft reconciliation remain acceptance gates.
7. Old clinician clients are fenced from writing once custody is installed and cannot read the new independent-key format. Coordinate backend/client deployment and document the minimum supported client; do not advertise legacy clients as compatible.
8. Patient recovery-kit creation/use currently belongs to the mobile flow. The web client copy no longer says recovery is impossible, but web does not implement a recovery-kit UI. Clinician TOTP backup codes recover the factor, not a forgotten account password.
9. Opt-in live/interoperability-generator tests are reported as skipped, not passed. Root owns live backend/browser integration logs and broader full-system readiness.
