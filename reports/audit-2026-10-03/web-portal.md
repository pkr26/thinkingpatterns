Audit date: 2026-10-03. Scope: all 185 git-tracked files under web/ (135) and portal/ (50). No app source was changed; temporary independently written probes were removed after execution. Review is source-based, with real React actions, WebCrypto and runtime probes. Rendered native-browser checks were blocked by the browser-control environment; visual layout, real screen-reader behavior, device microphone prompts, print rendering and production response headers are not independently certified here.

The machine-readable coverage manifest is `file-coverage.json`. Production TypeScript, React, tools, styles and configuration received complete executable/type/style reads in bounded sections (many comment-only lines were filtered). Tests were all executed where their normal gating allows, and every tracked test/helper received an AST-based structural scan; selected tests/helpers were also read in full or in relevant sections. Generated bilingual catalogs received key/placeholder parity checks and selected product-critical copy review, not a linguistic review of every translation. Those are deliberately different review depths: this is comprehensive file coverage, not a claim that every test assertion, translation, comment or binary byte was manually interpreted.

## Release-blocking verified defects

### WP-01 — HIGH: clinician password change silently leaves existing legacy notes unreadable

Evidence: `portal/src/views/PatientsView.tsx:268` defines rekeyLegacyNotes; calls at 292–300 and 315–323 bind legacy note decryption to the clinician **username**, and swallow decryption failure. `:411` invokes the migration with username, then the password wrap/credential rotations continue. Actual chart writes use the therapist UUID (`portal/src/views/PatientView.tsx:1155`, `:1212`). AES-GCM AAD is exact: UUID-bound real notes cannot decrypt under username-bound AAD. They are skipped; after the password changes the old password-derived legacy note key is gone.

Reproduction: create a real encrypted legacy note using UUID AAD and the old derived note key; invoke the actual PatientsView change-password action with real WebCrypto. Credential rotation succeeds, rekeyNotes is never called; old key still opens the note, freshly derived keys do not. This is a verified irreversible-access loss for valid legacy notes, not a remote authorization exploit. Fix: use immutable therapist UUID, include every revision, distinguish an already-v2 note from an unreadable note, fail closed on unreadable migration inputs, verify persisted migration before rotating credentials and use an atomic server transaction/recoverable envelope operation.

### WP-02 — HIGH: replacing the clinician sharing identity destroys v2 note access

Evidence: `portal/src/crypto.ts:50` derives noteKeyV2 from the P-256 PKCS8 private identity key. `portal/src/views/PatientsView.tsx:489` rotateSharingKey generates a fresh keypair and publishes it at 505–506, with no migration of current v2 notes/revisions. Copy at `:1262` promises “Your notes are unaffected.” They are affected.

Reproduction: create a real v2 note under the old identity-derived key; invoke the actual rotate-sharing-key action; decrypt the new wrapped identity and derive the new notes key. Neither new notes key nor unchanged legacy key can open the original v2 note. rekeyNotes was never called. Fix: create an independently generated durable notes key, wrap it under password/account custody independently of patient-sharing identity, and migrate existing notes/revisions transactionally. Until that exists, disable this destructive workflow or retain/migrate the old note key explicitly; correct the copy.

### WP-03 — HIGH: offline journal/safety-plan save can report success while persisting nothing

Evidence: `web/src/kvstore.ts:135` catches every setItem exception. OfflineQueue's writer therefore cannot report failure; `web/src/views/Entry.tsx:456` enqueue is followed by editor clear (`:471`), draft clearing and saved notification. `web/src/views/SafetyPlan.tsx:76` waits for the same storage abstraction then clears dirty state and says saved. Stored plan parsing also rejects strings >4,000 characters (`web/src/safetyPlan.ts:38`, `:68`), but the editor/save path does not enforce that maximum.

Reproduction: install a KvBackend that returns null and throws QuotaExceededError on write. enqueue resolves and queueLength is zero. A user is told the entry was saved, with no durable queue record. Fix: return a typed persistence failure; retain editor and encrypted draft until a committed write succeeds, use readback/transaction acknowledgement where needed, expose storage capability and never call an ephemeral-memory fallback “saved on this device.” Test quota, private mode, aborted IDB transactions, concurrent queue clearing and lock-during-save.

### WP-04 — HIGH: recording can begin after the entry screen is gone

Evidence: `web/src/audio/recorder.ts:193` awaits getUserMedia, then attaches the stream/starts MediaRecorder without an ownership-generation check. Unmount cleanup only sees streams already in refs. A second start while the first permission promise is pending also bypasses the guard, since no live ref exists yet.

Reproduction: call start with a deferred getUserMedia; unmount; resolve permission. MediaRecorder starts and the granted track is not stopped. Two pending starts grant two streams; cleanup stops only the latest stream. Entry's micBusy protects ordinary repeated clicks, but it does not fix late grants after leave/lock. Fix: synchronously reserve a pending acquisition slot; use an operation generation that reset/unmount invalidates, stop every late stream immediately, and guard/catch recorder.start. Include permission-denied/revoked and screen-lock races.

### WP-05 — HIGH: the patterns screen renders an unvalidated, replayed generation

Evidence: `web/src/views/Patterns.tsx:159` reconcile validates one insights response; `:186` fetches insights a second time; `:203` decrypts and `:205` renders that second payload without state_seq verification. A server/proxy can return fresh A then stale B; the visible B never passed the freshness check.

Reproduction: return validated seq20 first, validly encrypted seq1 second; mount the actual PatternsView. Old pattern label appears with no freshness error. Fix: reconcile must return the exact validated payload and the UI must render it, or validate the independently fetched second payload before changing state. Apply the ownership check to every delayed response.

### WP-06 — HIGH: writing entered during an in-flight save is erased

Evidence: `web/src/views/Entry.tsx:594` textarea remains editable while save awaits createEntry; completion clears text at `:471` regardless of whether it still equals the submitted content. Clearing active draft can also discard the later writing.

Reproduction: type old text, start save with a deferred API, type new writing while pending, then resolve. The real EntryView textarea becomes empty. Fix: clear only the submitted revision; preserve newer edits/drafts, or disable editing during the operation with an explicit saving state. The former provides a smoother experience.

## UX, clinical presentation and accessibility

The warm patient light/dark palette, restrained portal palette, explicit saved/queued language, safety/help access, empty states and disclosed privacy model are useful foundations. Source and automated checks show responsive breakpoints, safe-area spacing, focus visibility, reduced-motion support, password reveal, dialog management and intentionally excluded raw evidence from printed summaries. No screenshot-based beauty/usability score is claimed.

Improve the central daily task first: allow a mood/check-in-only entry, make “save” guarantee durability, retain concurrent writing and clearly distinguish local durable save from server receipt. Give users full read-only journal detail instead of requiring Edit to inspect content beyond preview truncation. Offer a calm weekly reflection with specific, user-correctable observations; show data coverage, uncertainty, recency and when evidence is insufficient. The initial day should be useful without a long run-up or a fake progress target. Avoid guilt/gamification around mental-health symptoms.

Use real URL-based navigation for history, patient chart and selected pattern, with back/forward/deep-link semantics and deliberate authentication restoration. Current in-memory view selection makes navigation/history inaccessible across reload and means offline writing works only in an already-loaded signed-in shell: no service worker/PWA and no offline password-unlock flow were found. Describe that limitation precisely or build a tested encrypted offline unlock/install experience.

Portal work should preserve draft notes before anything else, support quick patient search and a clean longitudinal chart, keep uncertainty/evidence secondary to the visit task, and add workflow controls that clinical users can act on (review/acknowledgment, follow-up planning and configurable sharing expiry) only with clear ownership. Add a TOTP QR enrollment path alongside manual secret entry. Clinical risk phrases/PHQ-9 flags are prompts to review, not automated diagnosis or proof of a monitored crisis service.

For accessibility, label every selection group programmatically; MoodScale/DotScale groups lack the naming consistency of BarScale. Instrument questions should own their radio-group semantics. Supply an accessible data table/summary for trend charts and dates/axis context instead of a generic chart aria label; distinguish trend scales explicitly (portal charts autoscale to observed maxima). Check touch targets,320px layout,200–400% zoom, keyboard-only complete flows, real VoiceOver/NVDA output, reduced-motion, dark mode and actual print output. Jest-axe in jsdom and token contrast math are useful but cannot certify these interactions. Spanish catalogs have excellent structural parity; native-language and clinical/cultural copy review remains needed.

The primary audit found backend brain `sample_days` populated by number of entries, not distinct days; patient `web/src/views/Patterns.tsx:332` labels it as days, while portal `PatientView.tsx:364` labels window entries. Make the protocol explicit (`entry_count`, `distinct_days`, effective independent observations) and render the correct unit. This matters for trust in pattern evidence.

## Architecture, performance, privacy and release quality

Split Entry, History, Settings, PatientsView and PatientView into cohesive workflow/state modules with typed state machines. Centralize operation ownership (account/session/patient/revision) instead of adding isolated mounted flags. Separate domain persistence success from platform fallback behavior. Model registration, processing consent, sharing, note key custody and credential rotation as recoverable transactions, not loose sequences of mutation calls. Improve runtime schema parsing; reduce scattered catch-and-null behavior that converts integrity errors into indistinguishable empty states.

Web initial JS is851.40kB (254.96kB gzip), with a bundler size warning. App eagerly imports all views, both catalogs and the generated bilingual lexicon. Lazy-load clinical/settings/history/sharing screens and locale/lexicon resources, move costly sentiment work off the main thread, debounce repeated100k-character text analysis, and measure input latency/startup on a low-end phone. History fully decrypts very large entry walks even if only30 rows render. Entry-version storage repeatedly loads/decrypts/rewrites a whole growing map per entry, yielding potentially quadratic startup/work; batch cache access and transactions, decrypt only needed pages, virtualize and add cancellation/progress. Preserve privacy while measuring durations/counts; never collect journal text, recording content, decrypt errors containing plaintext or identifiable clinical payloads.

Client transport has strong same-origin/TLS/redirect/no-cookie/no-referrer policies; keys and bearer tokens are kept in memory, encrypted data uses domain AAD, private keys are nonextractable handles, and processing/voice/sharing are explicitly consented. These controls are valuable. They do not make data absolutely zero-knowledge: consented processing and backend threats require the primary audit's broader backend assessment. Nor does SRI on a CSS file transitively authenticate referenced font bytes; SRI provides meaningful integrity only when the HTML defining expected hashes is itself trusted. Avoid overclaiming protections in comments or product copy.

Release criteria should be scenario-based: real keys+real persistence+real API+multiple clients+session teardown; deterministic clock/network/body-delay/storage-failure and every rotation failure boundary. Passing477 portal tests currently misses both demonstrated cryptographic note-loss paths. Test small useful invariants and full critical journeys rather than historical remediation assertion counts. Add browser E2E for account create→write→offline→reload→sync→share→note→rotate→unlock→revoke→export→delete, plus accessibility/manual clinical review. Mutation config has inPlace true; run it only in an isolated checkout and report actual results (not run here). Locks were reviewed, but lock integrity is not a vulnerability scan, and current advisory status requires the primary audit's dependency audit.

## Prioritized improvement program

1. **Release gate:** fixWP-01/02/03/04/05/06; add all12 independently exercised scenarios as tests expecting safe behavior; confirm every existing note/revision and queued item survives change/unlock/rollback. Ship no clinician rotation that silently destroys notes and no save confirmation that lacks durable data.
2. **Reliability and contracts:** atomic/recoverable credential+wrap+notes migration; storage-error propagation; mutation and body-session ownership; timeout through body; strict response schemas; fallback-lock exclusion; calendar and conflict preservation; align logout semantics, key schedules and data-count units across clients.
3. **Patient/clinician experience:** a fast minimal check-in, protected drafts, readable journal detail, robust chart/back navigation, clear local/server state and genuinely useful early reflections. Test with patients, clinicians and users of assistive technology; measure task completion, comprehension and recoverability, not only engagement.
4. **Performance and maintainability:** lazy bundles, worker/debounced NLP, batched encrypted maps, bounded/page-oriented decrypt/render, modular state machines and coherent error taxonomy. Set real budgets and validate on inexpensive devices and slow networks.
5. **Evidence and operations:** validate clinical interpretation/safety copy with qualified reviewers, prospectively evaluate heuristic calibration and uncertainty, monitoring/restore drills, independent security review and release gates. “Best ever” should become measurable goals: zero acknowledged-save losses, complete recoverability of critical operations, accessible task completion, useful accurate observations, fast response and trustworthy privacy claims.
